# Local API

The service listens on 127.0.0.1:4317. UI requests use a local session cookie and an exact allowed Origin. Start the service, open its one-time setup URL, then open the UI at http://127.0.0.1:4317 or http://127.0.0.1:5173. Hosted UI has no local connection.

JSON bodies and replies. Errors: `{error: string}`. AgentKlar IDs are UUID strings; native OpenCode session and message IDs use their own format. Ordinary API changes require authenticated UI or the private MCP bearer token. Approval decisions, instruction file changes, project skill changes and browser native setup writes require the UI cookie and exact local Origin. Browser native setup reads also require the UI cookie. A valid MCP bearer is rejected for every native setup request, including requests that also carry a UI cookie. Instruction text reads require the UI cookie; MCP receives metadata only. Skill previews require the trusted UI; MCP receives folder metadata only. Managed CLI onboarding uses the separate operator routes below.

The macOS service CLI uses separate private `/api/operator/*` routes for authenticated status, a fresh one-use setup link, onboarding, stop preparation and recovery. They require the saved operator key and managed service ID. Any browser Origin, cookie or Authorization header is rejected, including an MCP bearer. Neither the UI nor MCP exposes these controls. The new setup link expires after five minutes; creating one invalidates an earlier unused link without ending an existing browser session. Stop blocks new task starts before launch and refuses active workers unless `--force`; `start` resumes a service left paused by an interrupted stop command. The CLI checks launchd registration by command exit status and service health through this authenticated route. The human-readable `launchctl print` text is not parsed.

## Guided setup

- GET /api/onboarding: saved `{revision,projectId,mainHarness,updatedAt}`; UI only.
- PUT /api/onboarding: `{projectId,mainHarness,expectedRevision}` saves a registered project and installed main harness. A stale revision returns 409. `mainHarness:null` keeps the project without a main choice.
- GET /api/operator/onboarding: preferences, projects and selected native harnesses.
- POST /api/operator/onboarding/project: `{name,path}` uses the same project registration as the UI.
- POST /api/operator/onboarding/preferences: same revision-checked save as the UI.
- POST /api/operator/onboarding/setup: `{projectId,harness,operation}` for status or preview; apply also requires the saved `previewId`, undo the owned `changeId`.

Only the managed terminal operator can use these operator routes. Setup supports Codex, Claude Code, Muse, OpenCode and Antigravity. Both entry points use the same native setup manager, preview checks, ownership checks and native mutation fence. Active workers block native writes; quiescing blocks onboarding. Preferences record a choice, not verified account access. Operator setup exposes no worker approval action. MCP gains no onboarding tool.

- GET /api/health: `{ok:true}` (public).
- GET /api/snapshot: Snapshot in src/contracts.ts.
- POST /api/projects: `{name,path}` → Project. Path must exist and be absolute.
- PATCH /api/projects/:id: `{preference?,roles?}` → Project.
- GET /api/projects/:id/runs?limit=20&cursor=123: `{projectId,runs,nextCursor,hasMore}`. `limit` defaults to 20 and must be 1–20. The cursor is the positive decimal insert position returned by an earlier page; omit it for the newest page. Each run has its ID, state, harness, a 120-character prompt preview, timestamps, read-only flag, optional role and link IDs, workspace kind, and optional `launchSource`. Results, context, native homes, process IDs, workspace paths and routing bodies are omitted. Pages are ordered by insertion, so new runs and state changes do not shift an existing cursor. Unknown projects return 404; malformed IDs or query values return 400. Requires normal local UI or MCP authentication and returns `Cache-Control: no-store`.
- GET /api/projects/:id/lead: `{projectId,lead:ProjectLead|null}`. A live lead has `claimId`, `projectId`, nullable reported `clientName`, optional reported `clientVersion`, `claimedAt`, `lastSeenAt`, and `expiresAt`. The private bridge ID is never returned. Reading does not claim or renew. Unknown projects return 404.
- POST /api/projects/:id/lead: MCP bridge only. `{action:"claim"}` claims a free project or renews that bridge's existing claim. Another bridge's claim returns 409 with the current public lead. `{action:"takeover",observedClaimId}` replaces only that exact live claim in advisory mode; coordinated mode requires a reviewed handoff. An expired or changed claim returns 409. `{action:"release",observedClaimId}` releases only that bridge's exact live claim. All actions return `{projectId,lead}` and accept no client name or bridge ID in the body.
- DELETE /api/projects/:id/lead: trusted local UI only. `{observedClaimId}` clears only the claim still shown to that UI in advisory mode; coordinated mode requires the control recovery route with its current revision. A changed or expired claim returns 409. This does not stop a worker or change native permissions.
- POST /api/leads/renew: private MCP bridge heartbeat. `{claims:[{projectId,claimId}]}` accepts 1–16 distinct projects and returns only `{renewed:[{projectId,claimId}]}` for exact live claims belonging to that bridge. It never creates a claim. All lead responses use `Cache-Control: no-store`.
- GET /api/projects/:id/skills: metadata list of `.agents/skills` (`codex` target) and `.claude/skills` (`claude` target). The IDs select folders, not exclusive harness ownership: [OpenCode can read both](https://opencode.ai/docs/skills/) unless compatibility is disabled, and [Muse can read both project folders](https://meta-models.github.io/muse-code-sdk/next/guides/extend/skills/). External folders are labeled and never adopted. Authenticated local UI or MCP may read this route.
- POST /api/projects/:id/skills/preview: UI only. `{harness:"codex"|"claude",source:"owner/repo[#ref]",name:"exact-skill-name"}` → 10-minute preview with target path, source version/hash, full bounded SKILL.md text, and a complete file/folder manifest. `codex` writes to `.agents/skills`; `claude` writes to `.claude/skills`. Uses pinned `skills@1.7.0` in a private temporary folder; no project write. Native trust, compatibility, and activation decide whether a skill loads.
- POST /api/projects/:id/skills/install: UI only. `{previewId}` → managed install metadata. Rejects changed staged bytes, folder identities, or an occupied target. Never overwrites an existing skill.
- POST /api/projects/:id/skills/preview-update: UI only. `{installId}` → fresh 10-minute preview from that managed install's saved source, ref, name and harness. Includes current text/files, upstream text/files, `updateInstallId`, and `hasChanges`. Rejects edited or external skills; callers cannot supply a different source. No project write.
- POST /api/projects/:id/skills/update: UI only. `{previewId}` → updated managed metadata with the same install ID. Rejects changed current trees, changed staged bytes and superseded previews. Identical manifests return `unchanged:true` without a swap. A normal failed swap restores the unchanged prior tree. Conflicts or process interruption keep recovery trees with their location in the journal message; restart marks the operation interrupted and makes no recovery writes. Install and update previews cannot be used with the other action.
- POST /api/projects/:id/skills/remove: UI only. `{installId}` → removal metadata. Removes only an unchanged AgentKlar-owned project skill. A conflict leaves disk files alone.
- GET /api/skills: `{scope:"personal",checkedAt,skills}` for the server-selected user home. Lists `~/.agents/skills` and `~/.claude/skills` metadata. OpenCode can load both default personal folders unless compatibility is disabled; personal Muse loading is not verified. One durable owner record is shared across all registered projects; the route works without a project. UI or MCP may read this metadata, but pending preview text is not included.
- POST /api/skills/{preview,preview-update,install,update,remove}: trusted UI only. Uses the same strict request bodies, staging, review, update and guarded removal as the project routes. The server chooses the native user home; callers cannot provide a path or home. Preview and install IDs are scoped to personal skills and cannot be used on project routes, or vice versa. No MCP skill mutation or preview-text read is available.
- GET /api/projects/:id/catalog: cached CatalogSnapshot or null. This never launches a native read. Unknown projects return 404.
- POST /api/projects/:id/catalog: read native model catalogs and Codex account limits for the project folder. Concurrent reads for the same project share one request; completed results have a 30-second in-memory cache. Unknown projects return 404. Both catalog routes require normal local UI or MCP authentication.
- GET /api/benchmarks: read the bundled or saved last-good public LiveBench snapshot; this never downloads data. Normal UI/MCP authentication is required.
- POST /api/benchmarks/refresh: strict `{}` body; download only the two fixed reviewed public source files. UI requires its cookie and exact local Origin; MCP bearer is accepted. Extra fields are rejected. Concurrent refreshes share one download. Validated snapshots replace one SQLite cache row; errors return 503 and preserve last-good scores. Shutdown cancels and waits for pending refresh before closing storage.
- POST /api/projects/:id/recommend: `{roleId?,harness?,model?,complexity?,requiresImages?,requiresTools?,readOnly?,taskType?}` → WorkerAdvice. Complexity is `routine`, `standard` (default), or `hard`; image need defaults to false. `taskType` is `coding` (default), `reasoning`, `data-analysis`, or `language`. Uses service-read native metadata with the same 30-second catalog cache. Unknown project returns 404; unknown role, conflicting harness, unsupported role harness, extra fields or invalid values return 400. No worker starts.
- GET /api/projects/:id/context: `{projectId,revision,brief,memory,handoff,updatedAt,updatedVia}`. Unsaved context has revision 0, empty text and null update fields. Unknown projects return 404.
- PUT /api/projects/:id/context: `{brief,memory,handoff,expectedRevision}` → ProjectContext. All three text fields are required. Limits are 2,000, 4,000 and 2,000 characters respectively. The revision must be a nonnegative safe integer below the maximum safe integer. SQLite checks and saves the revision atomically. A stale writer gets 409 and must read the latest record and review its edits before retrying. The server records update time and authenticated channel (`ui` or `mcp`); clients cannot set them.
- POST /api/tasks/start: `{projectId,prompt,idempotencyKey,roleId?,harness?,model?,readOnly?,includeProjectContext?,routing?,followUp?,workspace?}` → Run. `workspace` is `project` (default) or `worktree`. A new worktree starts from local Git HEAD; it does not copy uncommitted or local-only files. Codex, Muse and OpenCode use an AgentKlar Git worktree; Claude uses native `--worktree` with `baseRef:head`, then AgentKlar checks its actual folder. The 202 response may show a planned path before Git preparation finishes. Worktrees and edits are retained after stop, failure, or restart. At most two workers run in one project, in separate checkouts; a busy checkout returns 409, including when registered again as another project. No queue, merge, or automatic removal runs. `routing:{complexity?:"routine"|"standard"|"hard",requiresImages?:boolean,requiresTools?:("web_search"|"image_generation")[],taskType?:"coding"|"reasoning"|"data-analysis"|"language"}` asks AgentKlar to select a model and start the worker in the same call; defaults are standard, false and coding within that object. If routing is absent, launch keeps manual/native-default behavior. `followUp:{runId,kind:"review"|"fix"}` links a completed run in the same project and inherits its exact workspace; a conflicting override returns 409. Review follows original work or a fix and requires `readOnly:true`; fix follows a review and requires `readOnly:false`. Active, interrupted, failed, cancelled, unknown, cross-project, or wrong-kind sources are rejected. Harness is `codex`, `claude`, `muse` or `opencode`; manual launch defaults to the selected role's harness, then Codex. An explicit harness must match the selected role and constrains routing. Saved context is included by default; set includeProjectContext to false to opt out.
- GET /api/runs/:id: Run.
- GET /api/runs/:id/context: `{runId,contextSnapshot:ProjectContext|null,followUpContext:FollowUpContext|null}`. Inspect saved project and linked source data captured at launch. Null means that part was absent.
- GET /api/runs/:id/tail?after=0: `{events:RunEvent[]}`.
- GET /api/runs/:id/result: result, state, error, tokens, native IDs, optional Muse subscription usage snapshot, compact `followUp` link metadata, saved `workspace` metadata, and optional `launchSource`.
- GET /api/runs/:id/handoff: read-only `RunHandoff` snapshot. `available:false` includes a precise `reason` and `command:null`; a ready packet includes `executable`, fixed `argv`, `cwd`, `env`, `envUnset`, `shell:"posix"`, and a quoted `display` command. Unknown runs return 404.
- POST /api/runs/:id/stop: Run.
- POST /api/approvals/:id: `{decision:string}` → `{ok:true}`. UI only, choices from Approval.decisions.

MCP tools: projects_list, project_runs_list, project_lead, project_register, project_update, project_instructions_list, project_context_read, project_context_update, harnesses_list, models_list, benchmarks_list, recommend_worker, task_start, run_status, run_context_read, run_tail, run_result, run_handoff, run_stop. `project_runs_list({projectId,limit?,cursor?})` uses the paginated route above. `project_lead({projectId,action,observedClaimId?})` has status, claim, release and takeover actions. `models_list({projectId,refresh?})` uses POST by default; `refresh:false` reads only the existing cache. Context tools use the same validation as HTTP. No approval tool.

CatalogSnapshot contains `projectId`, `checkedAt` and `harnesses`. Each Codex/Claude/Muse/OpenCode row contains `harness`, `models`, `modelsStatus`, `modelsMessage`, `modelsTruncated` and `quota`. Models have `id`, `name`, `description`, `resolvedModel`, `isDefault` and `inputModalities`. A model listing alone does not prove sign-in, subscription entitlement, model quality or actual charges. Descriptions are vendor text, which can include API prices or data-use terms. Codex models come from app-server `model/list`; Claude models come from the official SDK `supportedModels()` initialization read with waiting empty input, no prompt and no saved session. Muse models come from `muse serve --no-session-log` with `initialize`, `initialized`, and `model/list` only. All four can run workers. Muse and OpenCode are available by explicit harness or role choice; unpinned automatic advice excludes them. All catalog reads use the registered project folder and native settings. They create no worker or model turn. The Codex, Claude and Muse model probes have 12-second bounds. OpenCode bounds local-server startup and provider metadata separately. Each probe closes only its owned process group.

For Claude, `models_list` and the authenticated project catalog read also include optional `harnesses[].auth`: `status` (`signed_in`, `sign_in_required`, or `unknown`), `source` (`claude-auth-status`), and a fixed `message`. Refresh runs the installed [Claude Code CLI's `auth status`](https://code.claude.com/docs/en/cli-reference) with an eight-second bound. Only a valid first-party signed-out reply is treated as sign-in required; all ambiguous failures remain unknown. A known requirement excludes Claude from automatic routing but does not replace an explicit Claude pin. The native CLI's email, token, config path, and raw output are never returned or stored. This check does not verify model access, make a model call, or infer worker sign-in from the Desktop app.

OpenCode catalog refresh starts its own authenticated loopback `opencode serve` process in the selected project and reads `/provider` through the official SDK. It returns only models from connected providers with text input and tool calls. It keeps model ID, short name/description and text/image input flags; provider keys, headers and options are discarded. Native provider defaults are not labelled as the active project default. Account limits, access, quality and cost stay unknown. A refresh sends no prompt. The process and server password are not shared with callers and are closed after the read.

Quota has `status`, `message`, `ordinaryUsageAllowed` and `buckets`. Each bucket has `id`, `name`, `normalModel`, `primary`, `secondary` and `spendControlReached`. Windows have `usedPercent`, `windowDurationMins` and `resetsAt` in Unix seconds. Unknown values stay null. Reported percentages may exceed 100; clients may clamp a visual bar. Codex reads `account/rateLimits/read` with reset credit details excluded. A nonempty multi-bucket map takes priority over the legacy single bucket, so shared usage is not counted twice. The backend's ordinaryUsageAllowed value is preserved; percentages and reset times do not establish allowance or recovery. Claude quota is unavailable through this SDK read. Muse and OpenCode catalog refreshes do not read account usage; a model list does not establish remaining usage. Catalog and quota failures are independent and use fixed messages. Catalog rows are deduplicated, limited to 100 per harness and bounded in text length; shortened fields, invalid rows or incomplete pagination set modelsTruncated. Quota buckets are limited to 20 with a message when shortened. Model identifiers longer than 120 characters are rejected. Credits, balances, account IDs, emails and raw errors are omitted. AgentKlar stores catalogs only in this service's memory; they do not appear in `/api/snapshot`, the polling flow or SQLite and disappear on restart.

Additional compact reads: GET /api/projects and GET /api/harnesses. Snapshot and run status contain a 300-character prompt preview and a 1,000-character result preview with promptTruncated/resultTruncated flags. Result reads hold up to 24,000 characters with resultTruncated. Event tails fit 24,000 text characters and return `{events,nextAfter,hasMore,truncated}`; individual clipped events have textTruncated. MCP responses fit a bounded context budget and report an explicit truncated preview if a large collection exceeds it.

Each project keeps one latest context record in SQLite. Memory is manually saved text. AgentKlar does not automatically ingest transcripts or files or search vectors. Shared context is separate from the explicit native instruction editor below. At launch, nonempty context is captured as an immutable run snapshot with its revision and update source. Later context edits affect future launches. A run's prompt remains the original task. Worker adapters compose the same delimited JSON block of role and project data in the task prompt; native system instructions and permission rules still apply. Project data cannot grant approval or change harness policy. Saved text is capped at 8,000 characters; labels and metadata add a small fixed prompt overhead.

Task launch, idempotent replay, snapshot, run status, result and stop replies include contextRevision (or null) and omit the stored snapshot body. Use the explicit run context endpoint or run_context_read tool to inspect it. A model's own output may quote the context; AgentKlar does not remove text from worker results. Idempotency binds the context inclusion choice, so repeating the original launch returns its original run and captured revision even if project context has changed. Omitted and true inclusion are equivalent; false is a different launch input.

New runs also save an immutable `launchSource`: `{kind:"ui"}` for a local UI start, or `{kind:"mcp",clientName,clientVersion?}` from the MCP bridge's client metadata. Missing metadata and older runs have no source and display Unknown. MCP names and versions are bounded plain text and are self-reported by the client. This field is a start record, not authentication, ownership, or active lead presence. Clients cannot set it in the strict `task_start` body. An idempotent retry keeps the first run's source, even when a different client retries.

Linked runs also return `followUp:{kind,parentRunId,rootRunId}` in compact status and result reads. Their full `followUpContext` is only in the explicit context read. It freezes the original work prompt, the immediate source result, truncation flags, and source run ID, harness, model and completed state. Prompt and result are each capped at 8,000 characters; earlier results are not copied recursively. The worker prompt labels this source as untrusted task data. Linking never resumes a native session, starts another run automatically, or changes routing and native permission rules. The launch key includes the link input; a replay of the same key returns the saved run even if source results or project settings later change.

New runs include `harness`. Older runs without it used Codex. Run history may include roleSnapshot, effectiveModel, threadId and turnId when known. Routed runs also store a bounded `routing` record: selected harness/model and pin basis, saved preference, task needs, policy version, catalog time, and short reasons/warnings. The requested `model` and native reported `effectiveModel` remain separate. Claude's native session ID is recorded as threadId; no turn ID is invented. Claude tokens sum input, output, cache read and cache creation counts from the latest final native `modelUsage` once. These query pipeline totals include the main loop, subagents, sidechains and compaction. They exclude helpers outside that pipeline, such as permission classifiers and token probes. Missing, empty or invalid totals stay unknown. Native totals are estimates, not a billing statement; subscription spending remains unknown. Internal ownership fields are diagnostic data; callers do not own the worker process. Preference selects a model only when `routing` is present. A duplicate idempotency key must match the original validated launch inputs, including routing, and replays return the original run without fresh discovery.

OpenCode's native session ID is saved as `threadId` and its final root assistant message ID as `turnId`. A run completes only after the owned root session becomes idle, its final assistant step reports `finish:"stop"` with a completion time and no error, and no child session or unresolved approval remains. A `tool-calls` step alone cannot complete it. Valid root assistant token totals are summed only when the full bounded message list is available; otherwise tokens remain null. Native cost fields and provider secrets are not stored. New OpenCode runs also save bounded, nonsecret native path scope from the exact worker environment. After session creation, one bounded `opencode db path` metadata read records the exact database file. Failure only disables handoff; the worker continues. Inline config and permission values are never saved.

Muse runs may include `museSubscriptionUsage:{observedAtMs,weekly:{resetsAtMs,usedPercent},window:{resetsAtMs,usedPercent,windowDurationMins}}`. Times are Unix milliseconds; used percentages are nonnegative integers and may exceed 100. The owned Muse worker makes one `usage/read` request after its root turn ends, with a 750 ms limit. An empty, unsupported, invalid or timed-out read leaves this field absent and does not change the task result. Only these numeric fields are saved; tier, account details and unknown native fields are discarded. The snapshot can include work outside AgentKlar and is not a live balance, model-specific limit, or dollar cost. Older runs remain unknown. This field appears in compact snapshots, run status and result reads, but does not affect model advice. Muse's SDK client owns its connection's single notification handler, so this adapter uses the bounded read rather than replacing SDK event routing.

Native continuation stores resolved native scope at launch. [Claude's native config location](https://code.claude.com/docs/en/mcp-quickstart) changes when `CLAUDE_CONFIG_DIR` is set, even to `~/.claude`: an unset launch yields a command that unsets it in a subshell, while an explicit launch keeps the saved value. An unset Claude run also requires the same current user home. Older Claude runs without the saved set/unset scope are unavailable. A ready handoff requires a terminal run, valid native session ID, existing canonical saved checkout folder, installed matching CLI, and no active worker or possibly surviving process group in that checkout. Worktree handoff also checks the saved repository identity and branch. Codex resumes with its saved model when known and `--sandbox read-only` for read-only runs. Claude workspace-change runs use `--resume` with the saved model when known. Claude read-only runs are unavailable because the AgentKlar SDK hook limiting tools to Read, Glob, and Grep cannot be preserved by that native command. Muse 1.4.1 reports `museHome` during initialization and derives it from `XDG_DATA_HOME`; the handoff pins that parent directory and uses `muse resume <session UUID> --workspace <checkout> [--model <model>]`. Muse handoff requires the recorded data directory and rejects read-only runs. OpenCode uses its native `ses_` session ID and `opencode <checkout> --session <ID> [--model <provider/model>]`. The POSIX command restores saved XDG and OpenCode path settings, pins the exact database file, and requires the same user home. Old runs, transient inline settings, missing database metadata, changed data paths and read-only requests stay unavailable. No model catalog read, prompt replay, transcript copy, shell launch, new run, or acceptance change occurs. The packet does not transfer ownership or monitor manual work. Close the native session before launching another worker in that checkout.

Claude workers use the official `@anthropic-ai/claude-agent-sdk` with the installed Claude Code executable, native system prompt, settings and plugins. Discovery checks PATH, `~/.local/bin/claude`, then the newest executable desktop install under `~/Library/Application Support/Claude/claude-code`. Finding an executable does not verify sign-in or subscription access. Sign in through the native Claude Code CLI. AgentKlar does not read or copy login credentials, select an API key fallback, or log native auth events/stderr.

Existing native permission rules still apply. Only unresolved concrete Bash, Edit and Write actions can be answered through the trusted local UI, for that one action. Background commands, disabling the sandbox, requests for outside-path access, MCP questions and other unsupported prompts stop with needs_attention. No approval grants future permissions. A final root result and a drained SDK stream are required for completion; child output cannot complete the run.

OpenCode starts an owned authenticated local server and uses native permission requests. A supported `bash` request must expose a full bounded command. A supported `edit` or `write` request must expose an exact absolute target and full bounded diff or content. Only the trusted local UI can answer `once` or `reject`; broad or unsupported requests, owned child permissions, native questions and event reconnection stop with needs_attention. Unrelated sessions cannot approve or finish this run. Its native provider settings and permission rules are not changed.

Claude readOnly restricts model tool calls to Read, Glob and Grep. A PreToolUse hook denies every other tool, including Bash, MCP, Skill and Agent, before native auto-allow rules apply. Native configured hooks and runtime bookkeeping can still run and write files; this is a tool restriction, not an operating-system sandbox. Codex readOnly uses its native read-only sandbox. Muse and OpenCode have no worker read-only control; task_start rejects either when readOnly is true, including linked reviews. The worker adapters own detached local process groups, retain PID evidence for a possible surviving group, and terminate their group on stop.


Worker choice is a local policy calculation. The main native harness classifies task complexity and image needs, chooses any team role, and calls `task_start` with `routing:{complexity,requiresImages,requiresTools,taskType}` for automatic choice and launch. `recommend_worker({projectId,...})` is a preview only. Responsibility text belongs in the native task prompt; AgentKlar does not classify it using keywords or call another model to route work. The UI defaults to automatic choice for new tasks and also offers preview and manual/native-default launch. A no-choice decision returns bounded reasons and starts no worker. Discovery errors, a changed project, or a busy project require a fresh start request; there is no silent fallback after worker failure.

WorkerAdvice contains `projectId`, `createdAt`, `catalogCheckedAt`, `preference`, `complexity`, `requiresImages`, nullable `choice`, up to three `alternatives`, bounded `reasons` and `warnings`, `policyVersion`, `confidence:"limited"` and official `sources` URLs. Each WorkerChoice contains `harness`, `model`, optional `roleId`, `basis` (`task-pin`, `role-pin` or `policy`), `tier` (`efficient`, `balanced`, `capable` or `unknown`), reasons and warnings. Choices may contain compact `benchmark` reference evidence. Advice also contains `taskType` and `benchmarkMethod` (`reference-tie-break`, `policy-fallback`, or `pin`). No account record, raw quota, cost estimate or claimed saving is returned. Top-level warnings are capped at eight; each choice has at most four reasons and six warnings.

An explicit task model overrides a saved role model. Either pin is preserved exactly, including Claude aliases. A selected role fixes the harness; an explicit conflicting harness returns 400. An explicit model with no role or harness uses Codex, matching task_start. A pin blocked by native allowance, a relevant spend control, missing worker installation or missing required image evidence returns no choice and names the preserved pin. It never selects a replacement. A custom text model missing from the catalog can still receive pin advice with unknown capability and access warnings. Unknown image support cannot satisfy an image request.

Without a pin, advice considers only installed Codex/Claude worker adapters and native offered models. An explicit harness or selected role restricts that set. Muse and OpenCode have worker adapters but no reviewed cost or quality tier, so unpinned advice for either has no choice. Manual starts can use each native default. An explicit pin keeps `tier:"unknown"` and unknown billing and access warnings; OpenCode pins must match an exact connected text-and-tool `provider/model` ID. Exact reviewed model identities determine the Codex/Claude policy tier; unfamiliar releases have no inferred tier. Claude aliases use their native resolved model identity for automatic suggestions and tier/quota checks. Unknown aliases, default account alias and unreviewed Fable choices are not automatic candidates. Explicit aliases remain unchanged in pin advice. Codex image support requires `image` in the native input modalities; this Claude SDK does not report modalities, so Claude image support remains unknown.

Policy `2026-10-02.1` targets efficient for routine work, balanced for standard work and capable for hard work. Economical preference targets efficient for routine/standard and balanced for hard. Best targets capable and warns when headroom is low. Balanced preference uses capable for standard/hard when applicable native headroom is at least 50%, and efficient for routine/standard or balanced for hard when it is at most 20%. These thresholds are product rules. Their effect on subscription units is unknown. Automatic hard advice never uses the efficient tier. Candidates prefer the exact target tier, then the nearest reviewed tier; equal fits prefer known native included usage, then a fresh comparable benchmark score, then reviewed policy order. Scores can change order only within the same policy fit and known-allowance group, and only if every candidate in that group has comparable evidence. A lower or higher tier alternative includes a warning. Unknown usage allowance ranks behind a known allowed candidate of equal fit; unknown does not mean free, full, empty or blocked.

The reviewed Codex efficient order is gpt-6-luna, gpt-5.6-luna; balanced is gpt-6.1-sol, gpt-6-sol, gpt-5.6-sol, gpt-5.6-terra; capable is gpt-6-astra. A model is considered only if the native catalog offers it. gpt-5.5 remains unknown. Native instruction editing handles two files separately: root `AGENTS.md` (`agents`, shared by Codex, Muse and OpenCode) and root `CLAUDE.md` (`claude`, used by Claude Code and as a Muse/OpenCode fallback). [Muse](https://dev.meta.ai/docs/muse-code/configuration) and [OpenCode](https://opencode.ai/docs/rules/) prefer AGENTS.md at the project root. Creating it when CLAUDE.md exists may change which root file they read. No other file ID or arbitrary path is accepted. These are real project files. Their contents are neither copied into shared context nor injected into task prompts. Native settings, ancestor instructions, overrides and ongoing sessions decide what each harness loads; file presence alone does not prove loading. `AGENTS.override.md` presence produces a metadata warning without reading its contents. Native config, skills and authentication are not parsed or edited.

- GET /api/projects/:id/instructions: InstructionSnapshot `{projectId,checkedAt,files,changes}`. Each file has `{id,path,status,hash,bytes,message}`; status is `present`, `missing` or `unavailable`. This authenticated read is available to the UI and MCP. `project_instructions_list({projectId})` calls this route.
- GET /api/projects/:id/instructions/:file: InstructionDocument `{id,path,exists,hash,text,bytes}`. Trusted UI cookie required; any MCP bearer is rejected even when a UI cookie is also supplied. Missing files return empty text, zero bytes and null hash.
- POST /api/projects/:id/instructions/preview: `{file,text,expectedHash}` → InstructionPreview `{id,projectId,file,path,before,after,beforeHash,afterHash,createdAt}`. `before` is null for creation. Preview changes no file. It expires after ten minutes; this service retains at most 100 previews and discards them on restart.
- POST /api/projects/:id/instructions/apply: `{previewId}` → InstructionChange. Rechecks content and permission bits before saving. Undo text is durable in SQLite before the filesystem change. Preview IDs are one-use and scoped to the project.
- POST /api/projects/:id/instructions/rollback: `{changeId}` → InstructionChange. Restores the previous text and permission bits, or removes a file created by that change. It checks current text and permissions against the saved applied version. External changes return 409 and remain untouched. An already undone change returns 409.

InstructionChange contains `{id,projectId,file,path,createdAt,updatedAt,state,operation,beforeHash,afterHash,message}`. State is `prepared`, `applied`, `rolled_back` or `interrupted`; operation is `apply` or `rollback`. Inventory returns the last 20 metadata records; before/after text appears only in preview responses and the private SQLite journal. At most 50 finished records per project are retained; unfinished/interrupted records are retained for manual review. Restart marks a prepared record interrupted and performs no recovery writes. Explicit undo may recover an interrupted change only when the current file still matches its saved after version.

All instruction mutations use the native approval trust boundary: trusted UI cookie, allowed exact local Origin, and no MCP bearer. Text must fit 32 KiB in UTF-8 and contain valid Unicode text; BOMs are preserved. Reads reject oversized/binary files, symlinks, nonregular files and hardlinks. The registered real project folder is rechecked before writes. Writes use a temporary file, fsync and rename; existing permission bits are preserved, new files honor the service process umask. Ownership, timestamps, ACLs and extended attributes are not preserved. Ordinary hash checks catch observed edits; they cannot lock unrelated external writers through the final rename. No instruction bodies or undo text enter snapshot polling or MCP tools.


## Native MCP connection setup

- GET /api/projects/:id/setup/:harness: SetupStatus for `codex`, `claude`, `muse`, `opencode`, or `antigravity`. Reads native settings on demand. Only the trusted UI cookie is accepted. Returns the entry's `missing`, `configured`, `conflict` or `unavailable` state, scope, fixed message, checked time, latest managed change metadata and `canUndo`. It returns no native entry body, native output, full config or active-session health claim.
- POST /api/projects/:id/setup/:harness/preview: `{}` → SetupPreview. The destination must have no `agentklar` entry and no competing native scope. Shows only the app-generated `entry`, `configPath`, scope and Claude project `cwd`. Codex, Claude and Antigravity have a native `command`; Muse and OpenCode have `command:null` because setup edits their settings files. OpenCode's generated entry has `type:"local"`, a `command` array and `environment`. Saves a ten-minute, one-use in-memory preview. No native write occurs.
- POST /api/projects/:id/setup/:harness/apply: `{previewId}` → SetupChange. Fresh reads compare the destination, project identity and config snapshot before making the fixed change. Returns success only after a fresh read verifies the expected entry.
- POST /api/projects/:id/setup/:harness/undo: `{changeId}` → SetupChange. Removes only this app's saved, unchanged entry in the original project's selected scope. Existing exact entries are not adopted. External changes and scope conflicts return 409. An interrupted add or undo can be retried explicitly only if the current entry still matches; absent entries are not removed again.

OpenCode setup reads bounded local JSON/JSONC user, project, custom and managed layers directly. It does not call OpenCode's config-read command, which may write native files or install plugin dependencies. It preserves JSONC comments and unrelated fields, refuses ambiguous MCP variable expansion and competing entries, and writes only after a fresh file check. Its configured status means a local entry exists; remote settings and actual session loading are not verified. Native provider settings and permissions remain OpenCode's own.

Antigravity setup uses User scope and native `agy mcp add/remove` for `~/.gemini/config/mcp_config.json`. Its entry has `command`, `args`, `env` and `disabled:false`. Existing entries are not adopted; fresh config checks protect apply and unchanged-entry undo. Git projects must register the repository root. Setup checks the root workspace MCP file and refuses nested Git folders; parent workspace loading remains unverified. This is an MCP host connection only, with no worker adapter or native permission changes.

All setup writes require the trusted UI cookie and exact allowed local Origin. A valid MCP bearer is always rejected, including beside a cookie. Bodies are strict and accept no commands, arbitrary native config paths or replacement entries. Unknown projects return 404; unknown harnesses and extra fields return 400. Missing/stale previews or unknown change IDs return 404; observed config conflicts return 409. Unsupported or unsafe config reads return 422; interrupted command operations return fixed 503 messages. Config reads reject files larger than 2 MiB, symlinks, hardlinks, nonregular files and malformed relevant Claude JSON structures.

Codex reads only app-server initialization and `config/read` with `includeLayers:true` in the canonical project cwd. User-layer provenance must point to the expected native home and have no profile. Any other layer's `agentklar` definition blocks setup, even when it matches. No thread or turn starts. Claude reads only the exact project-local `mcpServers.agentklar` entry from its bounded JSON config, and checks global and committed `.mcp.json` definitions for scope conflicts. It does not use `claude mcp get`, which may start an existing server during its health check. Muse reads its user `muse/settings.json` under `XDG_CONFIG_HOME` or `~/.config`, and checks `.mcp.json` from the nearest Git root through the selected project. If no Git root exists, it checks the project folder. Old or mixed MCP key spellings and unsupported schema versions are unavailable until handled in Muse settings.

Codex and Claude add/remove use native CLI argv through spawn with no shell. Their native CLIs own config serialization and migrations. Muse has no global add command, so setup makes a guarded JSON change to `mcpServers.agentklar`. It keeps unrelated settings and file permissions, writes a new file with mode 0600, and replaces the file through an atomic rename. It does not rewrite old schemas. Command stdout/stderr fit 64 KiB, Codex config metadata fits 2 MiB and operations have ten-second probe timeouts. Timeout, shutdown and oversized output stop only the owned subprocess group. Native config/output and credentials are discarded. SQLite stores only the app-generated entry, ownership hash, destination, project identity and bounded change state. Prepared changes become interrupted at restart; no automatic recovery writes run. Snapshot checks cannot lock unrelated external writers through the final rename. Service startup, native session startup and native trust/permissions remain separate work.

## Optional human approval sharing

Ordinary peer grants and MCP cannot view or answer native approvals. Sharing is off by default and uses a separate private human capability, scoped to an existing owner project grant and exact source device. Settings creates a one-time code on the owner; the source imports it for its matching saved project mapping. Owner revoke and source remove are explicit UI actions. Tokens never enter snapshots, prompts, events or MCP.

`GET /api/peers/settings/human` returns secret-free configuration and bounded action-intent metadata. Grant/save/revoke/remove use trusted UI POST routes under that prefix. Remote list/read/answer use POST at `/api/remote-approvals/:dispatchId/list`, `/:approvalId/read` and `/:approvalId/answer`. Reads require `{}`; answers require one stable request UUID, the complete reviewed digest and an offered decision. These routes require the trusted local UI cookie, exact local Origin, and no Authorization header. Browser reads use POST so the browser supplies its natural Origin.

List returns bounded summaries. Read returns the exact complete supported request, digest and any saved intent or consumed receipt. Oversized/unsupported requests remain owner-UI actions. New answers require the live owner worker, exact pending approval and capability. The source saves a compact intent before transport. Unknown acknowledgment permits only the same request/digest/choice retry; reload recovers that intent. Definitive rejection requires a fresh complete read before a new explicit choice. Receipts are recorded/submitted/callback_failed and never prove native execution. Revoking either grant blocks remote reads, new answers and receipt replay. Native provider configuration and permission rules stay unchanged.

## Read-only native inventory

GET `/api/projects/:id/native-inventory` returns `{projectId,checkedAt,activationUnknown:true,harnesses,truncated}` for a registered project. Each harness has bounded `sources`, `extensions`, `extensionsTruncated` and coverage notes. Sources report path/scope/kind/presence and inspection limits. Extension records report name, version or null, source path, scope and cache/project-manifest evidence; activation remains unknown. No raw config values, credentials, native commands or enabled-state claims are returned.

The fixed-source read uses no CLI, network, write or model call. It accepts no arbitrary source paths or query parameters. Bounds are 40 sources, 24 extension records, 32 KiB per manifest, 256 KiB total manifest reads, 64 manifest attempts, 200 cache directories at fixed depth three, and a 22,000-character response. Partial observations are flagged. Settings requests this data only on explicit Refresh. This is source inventory, not plugin installation or general config management.

## Worker tool evidence

Model image input and worker tools are separate. `requiresImages:true` requires model image evidence. `requiresTools:["web_search","image_generation"]` requires fresh, complete native evidence for each requested tool on that exact harness/model. Unknown, incomplete, stale, or historical evidence cannot qualify a new worker. An explicit pin receives no replacement. A linked follow-up inherits omitted tool requirements; explicit `requiresTools:[]` clears them. The owner rechecks requirements before spawning a local or remote worker.

Catalog models may include bounded `toolEvidence` with tool names, source, timestamp and completeness. OpenCode advertises tool names without an agent/session scope, so its evidence remains incomplete. Claude runs may include `nativeTools` observed from the actual SDK init event. Historical run tools are observations, not proof for a new session. Read-only Claude workers are restricted to Read, Glob and Grep. No image generation worker has been verified.
